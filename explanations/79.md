# Problem 79: Passcode Derivation

https://projecteuler.net/problem=79

**Answer:** 73162890 · **Solution:** `P79.java` · **Runtime:** < 0.01 s

## Problem

A common security method used for online banking is to ask the user for three random characters from a passcode.
For example, if the passcode was 531278, they may ask for the 2nd, 3rd, and 5th characters; the expected reply
would be: 317.

The text file, keylog.txt (`data/keylog.txt`), contains fifty successful login attempts.

Given that the three characters are always asked for in order, analyse the file so as to determine the shortest
possible secret passcode of unknown length.

## In Plain Terms

Each login tells us three digits and the order they appear in: "317" means 3 comes before 1, which comes before 7.
Put all fifty of those "this comes before that" clues together and you can line the digits up. Whichever digit
never has anything before it goes first, then the next, and so on. If no digit repeats, the clues pin down a
single order.

## In Theory

This is a **shortest common supersequence** of the fifty 3-character strings. Assuming each digit appears once,
it becomes a **topological sort**: build a directed graph with an edge a → b whenever a comes before b in some
login, then order the digits so all edges point forward. The logins use eight distinct digits (4 and 5 never
appear), and the order is forced: 7, 3, 1, 6, 2, 8, 9, 0.

## In Code

The code builds the answer incrementally, without assuming digits are unique:

1. Keep a set of the shortest candidate passcodes consistent with every login so far (starting with the first
   login).
2. For each new login `xyz` and each candidate, find the cheapest way to make `xyz` a subsequence: already present
   (+0 characters); insert one missing character (+1) in each valid position; insert two (+2); or insert all three
   (+3).
3. Keep only the candidates of minimal length, and print one at the end.

## Complexity

Depends on how many minimal candidates survive each step — small for this input. Space O(candidates × length).

## Further Thoughts

The incremental search is more general than a topological sort (it would cope with repeated digits), but keeping
only the shortest candidates at each step is a greedy choice. A slightly longer intermediate could, in principle,
lead to a shorter final code. For this input, the topological sort agrees: 73162890.
