# Problem 14: Longest Collatz Sequence

https://projecteuler.net/problem=14

**Answer:** 837799 · **Solution:** `P14.java` · **Runtime:** ~1.1 s

## Problem

The following iterative sequence is defined for the set of positive integers:

```
n → n/2      (n is even)
n → 3n + 1   (n is odd)
```

Using the rule above and starting with 13, we generate the following sequence:

```
13 → 40 → 20 → 10 → 5 → 16 → 8 → 4 → 2 → 1
```

It can be seen that this sequence (starting at 13 and finishing at 1) contains 10 terms. Although it has not
been proved yet (Collatz Problem), it is thought that all starting numbers finish at 1.

Which starting number, under one million, produces the longest chain?

NOTE: Once the chain starts the terms are allowed to go above one million.

## In Plain Terms

Pick a number. If it's even, halve it; if it's odd, triple it and add one. Repeat until you hit 1. Some
numbers get there in a few steps; others bounce around for hundreds. We just try every starting number
under a million, count the steps, and keep the one with the longest journey. Nobody has ever proved every
number reaches 1 — but every number anyone has tried does.

## In Theory

There's no formula for chain length, so this is a **search**. Two observations help:

- Values can climb far above the start (837,799 peaks near 2.97 billion), so they need a 64-bit `long`.
- If n < 500,000 then 2n is also under a million and has a chain exactly one longer (2n → n → …).
  So the answer must be in the upper half.

The longest chain starting below one million begins at 837,799 and has 525 terms.

## In Code

1. Loop over odd `i` from 1 to 999,999 (`i += 2`).
2. `collatzNum` follows the sequence (as a `long`) until it reaches 1, counting steps.
3. Keep the `i` with the most steps.

## Complexity

About n/2 starting values times the average chain length (~100–150) — tens of millions of steps.
Space O(1).

## Further Thoughts

- **Skipping even starts is a fragile assumption.** The halving argument above only rules out evens
  *below 500,000*; an even start between 500,000 and a million could in principle win. It doesn't here,
  but the bound `i` from 500,001 upward over all numbers is the airtight version (and also halves the work).
- **The cache doesn't do anything.** `collatzNum` checks a `chains` map that is never filled, and the map is
  keyed by `Integer` while the lookup passes a `long` (boxed as `Long`), so it could never match anyway.
  Storing each starting number's length — and looking up any value below a million — would make this
  several times faster. This is **memoization**.
