# Problem 87: Prime Power Triples

https://projecteuler.net/problem=87

**Answer:** 1097343 · **Solution:** `p087.py` · **Runtime:** ~0.1 s

## Problem

The smallest number expressible as the sum of a prime square, prime cube, and prime fourth power is 28. In fact,
there are exactly four numbers below fifty that can be expressed in such a way:

```
28 = 2² + 2³ + 2⁴
33 = 3² + 2³ + 2⁴
49 = 5² + 2³ + 2⁴
47 = 2² + 3³ + 2⁴
```

How many numbers below fifty million can be expressed as the sum of a prime square, prime cube, and prime fourth
power?

## In Plain Terms

We want numbers that can be built as one prime squared, plus one prime cubed, plus one prime to the fourth power.
My first worry was that checking every number up to fifty million would take forever, but it turns out you don't
need to: the powers grow so fast that only a few dozen primes can be cubed or raised to the fourth power, and
under a thousand can be squared. So I flip it
around and build every possible sum from those primes, ticking each one off on a checklist of all the numbers below
fifty million. Ticking a number twice doesn't count it twice, which matters because some numbers can be built in more
than one way. The answer is how many numbers end up ticked.

## In Theory

**How big can each prime be?** Every term is positive, so each one alone has to be below fifty million:

```
p² < 50,000,000   →  p < 7,071   →  908 primes
q³ < 50,000,000   →  q < 368     →   73 primes
r⁴ < 50,000,000   →  r < 84      →   23 primes
```

That's at most 908 × 73 × 23 ≈ 1.5 million combinations, and stopping each loop as soon as the sum reaches fifty
million cuts it to about 1.14 million. Small enough to try them all.

**Count numbers, not combinations.** Different prime triples can give the same total. Of the 1,139,575 combinations
under the limit, only 1,097,343 distinct numbers come out, so about 42,000 totals are reached more than once.
Counting combinations instead of numbers would overshoot. A hash set, or a yes/no slot for every number,
keeps each total once.

**The example:** below 50 the only sums are 28 = 2² + 2³ + 2⁴, 33 = 3² + 2³ + 2⁴, 47 = 2² + 3³ + 2⁴ and
49 = 5² + 2³ + 2⁴.

## In Code

1. List the primes below √limit with `sympy.primerange`, then work out every prime square, cube and fourth
   power below the limit once, up front: 908 squares, 73 cubes and 23 fourth powers.
2. Make `seen`, a numpy array of fifty million yes/no slots, one per number below the limit. Marking a slot that's
   already marked changes nothing, so a number reached several ways still counts once. That's the job the set
   did, without any hashing.
3. Loop over every (fourth power, cube) pair, only 23 × 73 = 1,679 of them. For each pair, two **bulk** numpy
   steps:
   - `squares + (fourth + cube)` adds the pair to **all 908 squares at once**, giving 908 totals.
   - `seen[totals[totals < limit]] = True` keeps the totals below the limit and marks all of them in one go.
4. `seen.sum()` counts the marked slots, again in one bulk step.

"Below fifty million" is strict, so a total of exactly 50,000,000 isn't counted.

**Why bulk is faster.** The work is the same, about 1.1 million additions, but *who* does it changes. In a plain
Python loop, every single addition goes through Python's interpreter, which costs far more than the addition itself.
Here Python only runs the outer 1,679 loop steps, and numpy does the ~1.1 million additions and marks in compiled
code, many at a time. That's the usual way to speed up Python: the same idea, done in bulk.

## Complexity

About 1.1 million additions and marks, so O(π(√L) × π(∛L) × π(L^¼)) for a limit L, but only 1,679 of those
steps are Python loop iterations. The `seen` array takes L bytes (50 MB).

## Further Thoughts

- **Before and after.** The first version looped over every combination in plain Python and kept totals in a set:
  about 0.5 s. Working the powers out once beforehand brought it to about 0.3 s, and the bulk numpy version takes
  about 0.1 s, with the same answer.
- **A runner fix that came out of this:** the runner used to start its timer before importing the problem, so
  library start-up (about 1 s for numpy and sympy) was counted as solving time. That's why this problem first
  looked like it took 1.2 s. It now times only `solve()`.
- **No shortcut for the duplicates.** No term can equal another kind of term (p² = r⁴ would need p = r², which
  isn't prime), so duplicates are whole sums that happen to coincide. There's no pattern to predict them, so every
  total has to be computed and checked off.
